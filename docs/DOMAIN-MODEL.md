# DOMAIN-MODEL — Glossary, entities, state machines, permission keys

Shared vocabulary for every QSPS ticket. Use these names in table, contract, module, and screen names. Section references (§) are to the TOR. In the repository this is `docs/DOMAIN-MODEL.md`.

## 1. Glossary

| Term | Meaning |
| -- | -- |
| **Client** | A registered member of the public. Owns Bookings, Payments, and Documents. |
| **Staff user** | A BOQ employee account. Holds one or more Roles and a set of Scopes. |
| **Role** | A named, admin-editable bundle of Permissions. The seven TOR roles (Annex A) are seeded Roles. |
| **Permission** | One key the API checks before an action. Format in section 2. |
| **Scope** | The Service Categories and Locations a Staff user may act on. Empty scope means nationwide and is reserved for Super Admin, System Admin, and Auditor. |
| **Location** | A BOQ office where services are rendered (Manila, Cebu, Davao…). Called station, branch, or satellite office in the TOR. |
| **Service Category** | A BOQ service area: `immunization`, `physical-exam`, `sanitation`, `food-safety`, `human-remains-bio`, `food-export-water`, `cashier`, `rco`. The TOR's "module". |
| **Service** | One bookable, priced item inside a Service Category, such as yellow fever vaccination or the basic hygiene seminar. |
| **Schedule Slot** | Capacity for one Service at one Location on one date and time window. |
| **Form Template** | An admin-built questionnaire attached to a Service. A client's answers are a **Form Submission**. |
| **Booking** | One checkout by one Client. Has a Reference Number and one or more Booking Items. The TOR's "transaction". |
| **Booking Item** | One Service in a Booking, with its own Schedule Slot, fee, and processing status. The TOR's "transaction component". |
| **Reference Number** | System-generated unique Booking identifier, printed as text and QR code. |
| **Hold** | The period a slot stays reserved for an unpaid Booking before auto-cancel. |
| **Expedite Booking** | A client request for a date with no open slots; needs staff approval. |
| **VIP Booking** | A staff-created Booking that bypasses slot capacity. |
| **Payment** | One attempt to pay a Booking through a Payment Channel. |
| **Payment Provider** | A gateway integration behind the `PaymentProvider` interface, identified by a code. `linkbiz` and `onsite` are fixed; online gateways are added as adapters under their own code. No gateway is hard-wired. |
| **Payment Channel** | What the client picks at checkout: GCash, Maya, card, BancNet, GrabPay, 7-Eleven, `Link.Biz`, onsite cashier. Each maps to one Payment Provider. |
| **Convenience Fee** | A per-channel charge added at checkout and itemized on the Receipt. |
| **Receipt** | The e-Receipt issued for a successful Payment. |
| **Refund Request** | A tracked request to return or forfeit a paid amount. Money moves outside the system. |
| **Assessment** | A Staff user's verification of one Booking Item: clear, return for correction, or reject. |
| **Document** | An official output issued for a cleared Booking Item: certificate, permit, vaccination record. Carries a Document Number and a Verification Token. |
| **Verification Token** | Unguessable value in a Document's QR code; the public portal looks the Document up by it. |
| **Policy** | A named, admin-editable rule value: hold minutes, arrival cutoff, reschedule limit, forfeiture rule. |
| **Audit Entry** | An append-only record of one user or system action. |
| **Notification** | An outgoing email, SMS, or push message, queued in the outbox. |
| **Sync Operation** | One staff action captured offline and replayed to the API. |
| **Import Batch** | One run of the legacy import pipeline. |
| **System** | The automated actor: sends Notifications, expires Holds, runs sync. Audit Entries by System have no actor user. |

## 2. Permission-key convention

```
<module>.<submodule>:<action>        e.g.  bookings.expedite:approve
```

* `module.submodule` is the template's "resource"; `action` is the verb. The colon is kept because `RbacService` matches wildcards on the text before it: a role holding `bookings.expedite:*` satisfies any `bookings.expedite:<action>`.
* Every key lives in `PERMISSION_NAMES` in `packages/contracts/src/modules/v1/rbac/rbac.catalog.ts`. Unknown keys fail closed.
* Routes declare keys with `@RequirePermissions(...)`; `RbacGuard` enforces them. A denial returns 403 and writes an Audit Entry with outcome `denied`.
* A permission answers "may this user do this kind of thing". Scope answers "on which records". Both are checked on the server (Flow A in the TICKETS document).
* User stories name the key; acceptance criteria and technical notes enforce the same key.

## 3. Entities and relationships

```
role >──< permission                      (role_permissions)
role >──< user ──< user_scope >── service_category
                        └──────>── location

service_category ──< service ──< schedule_slot >── location
                        └──< form_template ──< form_field

user(client) ──< booking ──< booking_item >── service
                    │             ├──>── schedule_slot
                    │             ├──< form_submission
                    │             ├──< assessment >── user(staff)
                    │             └──< document
                    ├──< payment ──< payment_event
                    │       └──── receipt
                    └──< refund_request

payment_channel >── payment_provider (code)
policy · policy_document ──< policy_acceptance >── booking
announcement · notification · device_token
audit_log · sync_operation · import_batch ──< import_row
user ──< password_history
user ──── mobile_verification_challenges      (one pending code per user)
sms_code_limits                               (per number and per account)
```

## 4. Core tables and lifecycle notes

All tables are defined with `createTable` in `packages/db/src/schema.ts`. Money is integer centavos. Timestamps are UTC; business dates are computed in Asia/Manila.

| Table | Key columns | Lifecycle notes |
| -- | -- | -- |
| `users` (template) | * `account_type` (`client`/`staff`), `mobile`, `gender` (free text), `birth_date`, `nationality`, `legacy_id`, `must_reset_password`, `password_changed_at`, `disabled_at`, `deleted_at`, `two_factor_enabled`, `mobile_verified_at?`, `sms_notifications_enabled` (default false), `mfa_otp_channel` (`email`/`sms`, default `email`), `privacy_notice_version?`, `privacy_accepted_at?` | Never hard-deleted; disabled or soft-deleted instead (`deleted_at` excludes the account from the default list while keeping history and audit entries). `two_factor_enabled` is set by Better Auth once a second factor is enrolled (AUTH-2). `password_changed_at` is set each time a password is set or changed (AUTH-3); null means unchanged since `created_at`. A staff account whose password is older than the `auth.staff_password_max_age_days` Policy gets `must_reset_password` at sign-in and must set a new password before anything else. Failed sign-in counts and account lockouts (AUTH-3) live in Redis, not on this table. NTF-2: `mobile_verified_at` is set when the client confirms a code sent to `mobile`; changing `mobile` clears it and turns `sms_notifications_enabled` off. SMS notifications need a verified number. `mfa_otp_channel` chooses where the AUTH-2 one-time sign-in code goes; `sms` needs a verified number and an enrolled second factor, and changing it needs the password. PRC-2: a Processing Officer can create a client account for a walk-in (`WalkInService`). The account has no password, `email_verified = true` and `must_reset_password = true`, gets the Client role, and is sent the Better Auth set-password email (the same invitation as ADM-1 staff accounts); setting the password clears `must_reset_password`. A new account is refused when any account already has the email (case ignored) or the same last ten digits of `mobile`. PRC-2b: the walk-in needs an email or a mobile number. A mobile-only account stores the placeholder `<id>@no-email.invalid` (Better Auth needs an email; `.invalid` can never receive mail), has `email_verified = false`, and is sent no invitation until a real email replaces the placeholder at the counter (then the invitation goes out) or SMS invitations exist (NTF-2). The mailer skips every `.invalid` address. The placeholder is never shown as an email: display responses carry `null` and screens say "No email". Privacy consent: `privacy_notice_version` is the Privacy Notice version the client accepted and `privacy_accepted_at` when (set at sign-up, AUTH-1, or at the counter, PRC-2b, in the walk-in transaction). A client whose version is missing or older than the current notice is asked to accept it before the portal opens; accepting stamps both columns again. |

Written only by the Better Auth two-factor plugin; the secret and recovery codes are stored encrypted. Five consecutive wrong codes lock the challenge for 15 minutes. MFA is mandatory for `account_type = staff` and optional for clients. |

Database trigger rejects update, delete, and truncate for every role. `entry_hash` is sha256 of `prev_hash` plus the row's fields, so `pnpm audit:verify` finds any row changed outside the application. Rows from before FND-3 have no hash. System actions have no actor, role, IP, or user agent; `domain` names the job. |
| `locations` | `id` (primary key), `code` (unique, uppercase), `name`, `address`, `region`, `is_active`, `card_offset_x_mm`, `card_offset_y_mm` (real, default 0) | Disabled locations are excluded from new-booking pickers; existing bookings are unchanged. Physical deletion is refused until booking references can be checked. CRT-3: the card offsets shift the vaccination card print for that station's passbook printer (positive X right, positive Y down, -30 to 30 mm, rounded to 0.1 mm); set on the Locations screen and audited with the other Location fields. |
| `service_categories` | `code`, `name` | Seeded with the eight codes in the glossary. |
| `services` | `service_category_id`, `code`, `name`, `fee_centavos`, `requires_approval`, `document_type?`, `auto_issue` (default true), `is_active` | Fee changes apply to new Bookings only. `document_type` is a key in the document-type registry that a Service can issue (currently `icv-record`, `sanitary-permit`, `ship-sanitation`, `food-safety-training` and `haccp`) or null; free text is refused. `medical-exemption` is issued in place of `icv-record` and is never set on a Service (CRT-3). When `auto_issue` is on, the Document is issued in the same transaction that makes a Booking Item `cleared`: the officer's clear when no head approval is needed (CRT-1), a head approval, or an override (CRT-1a). `issued_by` is whoever made the item cleared; they enter the certificate details or, for a vaccination Service, record the medical exemption instead (CRT-3). CRT-5: only `icv-record` is issued on clearance. The `sanitary-permit` and `ship-sanitation` Services (category `sanitation`) are seeded inactive, with no fee, `auto_issue` off and a published questionnaire, and an admin sets the fee and switches them on; even with `auto_issue` switched on they never issue on clearance, because the officer issues the document from the item (`certificates.documents:issue`) and enters its validity period there. CRT-6: the `food-safety-training` Service (Basic Hygiene and Sanitation Seminar) and the `haccp` Service (GMP-HACCP Audit), both in category `food-safety`, are seeded the same way (inactive, no fee, `auto_issue` off, published questionnaire). A seminar session is an ordinary `schedule_slots` row of the seminar Service, so clients book it and capacity works as for any slot; staff list the sessions of a day and their roster from the Service's slots, and no table is added. Neither type is ever issued on clearance. CRT-7: the `human-remains` Service (Human Remains Transport Clearance), the `biological-certification` Service (Biological Substance Certification) and the `biological-permit` Service (Biological Substance Permit), all in category `human-remains-bio`, are seeded the same way (inactive, no fee, `auto_issue` off, published questionnaire). None is issued on clearance: the officer issues each from the cleared item. |
| `schedule_slots` | `id` (primary key), `service_id`, `location_id`, `starts_at`, `ends_at`, `capacity`, `booked_count`, `is_disabled`, `disabled_reason?` | Unique on `service_id`, `location_id`, `starts_at`. `booked_count` changes only inside the booking transaction (Flow B). Capacity cannot go below `booked_count`; a slot with bookings is disabled, never deleted. A disabled slot takes no new bookings and keeps existing ones. SCH-2: a bulk capacity change covers one Manila day, Monday-based week or calendar month and leaves any slot whose `booked_count` is above the new capacity unchanged, listing it back. Blocking a date sets `is_disabled` and `disabled_reason` on that date's slots; a slot already disabled by hand keeps `disabled_reason` null, so unblocking the date (which clears only slots with a reason) leaves it disabled. Paid Bookings on a blocked date are listed for follow-up and never cancelled automatically. |
| `form_templates`, `form_fields` | `service_id`, `purpose` (`questionnaire`/`step_result`, default `questionnaire`), `service_step_id?`, `version`, `status` (draft/published/retired), `is_active`, `published_at`, `created_at`, `updated_at`; field `form_template_id`, `type`, `label`, `required`, `options` (jsonb, choice types only), `position` | Editing a published template creates a new version. One draft and one published version per Service (partial unique indexes); publishing retires the previous published version and keeps it. A version with Form Submissions cannot be deleted, only disabled (`is_active` false) (FRM-1). PRC-4: `purpose = step_result` marks a Service Step's result form, with `service_step_id` set; it is versioned per step (unique on `service_step_id`, `version`, one published version per step) and never has a draft: saving changed questions publishes the next version and retires the previous one, which is kept for the results recorded against it. Step result forms have no file questions. The questionnaire rules above and the FRM-1/FRM-2 screens apply to `purpose = questionnaire` only; the questionnaire unique indexes are partial on that purpose. |
| `form_submissions` | `booking_item_id` (unique), `form_template_id`, `answers` (jsonb), `created_at` | Written by `BookingService` in the transaction that creates the Booking (FRM-2), against the Service's active Form Template version (published and enabled); answers are keyed by form field id and checked with `checkFormAnswers`, the same rules the web uses. The client may replace them while the Booking is `pending_payment`; immutable after payment, staff corrections go in `assessments`. A file answer is uploaded to `form-uploads/pending/<user_id>/<uuid>.<ext>` (`FileStorage`: PDF, JPG or PNG up to 5 MB, content checked) and copied to `form-uploads/<user_id>/<uuid>.<ext>` when the answers are saved; the stored answer always holds that confirmed key (FRM-2b). A daily job (03:00 Asia/Manila) deletes pending files older than 24 hours; confirmed files are kept. One submission per Booking Item. Staff with `processing.queue:read` whose Scope covers the item can download a file answer from Assessment (FRM-2c); each download is audited as `form_upload.read`. |
| `service_steps` | `id` (primary key), `service_id`, `name`, `position` (0-based), `required` (default true), `is_active` (default true), `created_at`, `updated_at` | PRC-4: the ordered stations a Service's Booking Items pass through. Configured on the Service by holders of `settings.services:manage` within their Scope; each step has one published result form (`form_templates`, `purpose = step_result`). A step with recorded results is never deleted, only disabled; a disabled step is no longer required and takes no new results, and its earlier results stay readable. A Service with no active steps is assessed exactly as before. |
| `step_results` | `id` (primary key), `booking_item_id`, `service_step_id`, `form_template_id`, `version`, `answers` (jsonb), `recorded_by`, `created_at`, `released_at` (nullable) | Result versions and answers are insert-only. Unique on `booking_item_id`, `service_step_id`, `version`. A correction inserts the next version and keeps earlier versions. The highest version is current. Answers are keyed by form field ID and checked with `checkFormAnswers` against the published result form. Staff with `processing.assessments:perform` record results at the item's station while it is `checked_in` or `in_assessment`. The first result moves a `checked_in` item to `in_assessment` through `BookingService`. Records and corrections are audited as `step_result.record` and `step_result.correct`. For Physical Examination, answers are encrypted at rest and omitted from audit entries. The authorized physician may update only `released_at` on current versions. Corrections start unreleased. The Booking owner can download the summary only when all three current results are released. Public verification never returns the results. A required active step must have a recorded result before clearance, including head approval and overrides. A rejected item missing a required step cannot be overridden, and no one records results on a rejected item. |
| `bookings` | `id` (primary key), `reference_number` (unique, `QSPS-YYMMDD-XXXXXX`), `client_id`, `status`, `kind` (`regular`/`expedite`/`vip`/`walk-in`), `total_centavos`, `hold_expires_at`, `pay_onsite` (default false), `cancel_reason?` (`hold_expired`/`no_show`/`client_cancelled`), `cancelled_at?`, `created_by` | State machine 5.1. Only `BookingService` changes `status`. `hold_expires_at` is set from the hold Policy (`booking.hold_minutes`, ADM-6). BKG-2: `pay_onsite` is set when the client chooses to pay at the BOQ cashier; the hold then no longer applies and `hold_expires_at` is cleared. The expiry job (`apps/backend/src/common/maintenance/`, every minute) cancels a `pending_payment` Booking with reason `hold_expired` once `hold_expires_at` passes (online only), or with reason `no_show` once its earliest slot starts within `booking.arrival_cutoff_minutes` (any unpaid Booking). Both wait while the Booking has an `initiated` or `pending` Payment updated within the last 60 minutes and started within the last 24 hours, since money may still arrive (PAY-6 deferral rule: the re-query job touches the Payment each time the provider still says pending, so an over-the-counter payment keeps its Booking for up to 24 hours). The client can cancel their own unpaid Booking (`bookings.own:cancel`, reason `client_cancelled`). `cancel_reason` and `cancelled_at` are set only together with `status = cancelled`; every cancellation releases one place in each item's slot in the same transaction. A client has at most one `pending_payment` Booking; booking again is refused with that Booking's Reference Number. PRC-2: a walk-in Booking has `kind = walk-in`, `client_id` = the client and `created_by` = the Processing Officer who encoded it. It goes through `BookingService.create` like any other Booking and starts `pending_payment` with the usual hold, payable at the cashier. Its slots must be today's, at the officer's Location; a slot that has started but not ended may be booked. The expiry job does not apply the `no_show` arrival cutoff to walk-ins (the client is already at the office); `hold_expired` still applies. |
| `booking_items` | `id` (primary key), `booking_id`, `service_id`, `schedule_slot_id`, `location_id`, `fee_centavos`, `reschedule_count` (default 0), `status` | State machine 5.2. `fee_centavos` is the Service fee at booking time. BKG-5: the client moves a `booked` item of their own `pending_payment` or `paid` Booking to another open, not full, not started slot of the same Service and Location (`bookings.own:reschedule`). Both slots are locked in id order in one transaction (Flow B); the old slot's `booked_count` drops, the new one's rises and `reschedule_count` goes up by one. Payments are never touched. Refused (409, with the rule) once `reschedule_count` reaches `booking.max_reschedules` or within `booking.reschedule_min_hours_before` of the current slot. Audited as `booking_item.reschedule` with the old and new slot, and the client is notified (`booking_rescheduled`). CRT-6: a seminar session's roster is the items booked into its `schedule_slot_id`; marking attendance moves them through `BookingService` only. |
| `payment_channels` | `code`, `name`, `provider_code?`, `convenience_fee_centavos`, `convenience_fee_bps`, `is_enabled`, `created_at`, `updated_at` | Switching provider is a row update, read on every payment, so it needs no deployment (PAY-5). `provider_code` is null until an administrator assigns one, and a channel cannot be enabled without it. Convenience fee = `convenience_fee_centavos` + `convenience_fee_bps`/10,000 of the Service fees, rounded half up to the centavo (`chargeFor` in the payments module, used by checkout and `PaymentService.create`; the Receipt prints the Payment's stored figures). Changes apply to new Payments only and are audited with old and new values. Seeded with TOR §VIII.2's channels, all disabled. `payments.channel_code` has no foreign key, so Payments made before a channel row existed stay valid. |
| `payments` | `id` (primary key), `booking_id`, `channel_code`, `provider_code`, `provider_reference`, `amount_centavos`, `convenience_fee_centavos`, `status`, `needs_review`, `collected_by?`, `tender_type?` (`cash`/`card`/`check`), `review_resolution?` (`rebooked`/`refund_requested`), `review_note?`, `rebooked_booking_id?`, `reviewed_by?`, `reviewed_at?` | State machine 5.3. `amount_centavos` is the full amount charged: the Booking total plus `convenience_fee_centavos`. `(provider_code, provider_reference)` is unique. One `succeeded` Payment per Booking is the rule; it is enforced in `PaymentService.confirm`, not by a unique index, because a second success is real money and must still be recorded, with `needs_review` set. `needs_review` is also set for a late success on a cancelled Booking (D7). Onsite payments (PAY-4) have `channel_code` and `provider_code` `onsite`, no convenience fee, and `collected_by` and `tender_type` set; they are created and confirmed in one transaction through `PaymentService.collectOnsite`, and the `onsite` provider accepts no notifications. PAY-6: a `pending` Payment not heard from for 10 minutes is re-checked with the provider's `queryStatus` by the job in `apps/backend/src/common/maintenance/` (every 5 minutes); the answer goes through `confirm`, or moves the Payment to `failed`/`expired`; "still pending" touches `updated_at`. A second success on a paid Booking is a duplicate: `needs_review`, no second Receipt. A `needs_review` Payment with no `review_resolution` is an open exception; staff resolve it once (`bookings.all:override`), recording how, why, who and when, and it is audited. |
| `payment_events` | `payment_id?`, `provider_code`, `provider_event_id` (unique per provider), `payload`, `signature_valid`, `processed_at`, `created_at` | Raw log of every provider notification, stored before it is checked. Insert-only; `processed_at` is the one later write. `payment_id` is null when the notification names no known payment. An event whose signature does not verify is stored under `unverified:<sha256 of body>` instead of the provider's event id, so a forged event can never block the real one as a duplicate. |

## 5. State machines

### 5.1 Booking (the centre of the system)

```
                    ┌── rejected
pending_approval ───┤                         (expedite only)
                    └──► pending_payment ──► paid ──► completed
                              │               │
                              ▼               ├──► forfeited
                          cancelled           └──► refund_requested ──► refunded
```

| Transition | Trigger | Guard |
| -- | -- | -- |
| → `pending_payment` | Client books (or expedite approved) | Slot capacity available; client has no other unpaid Booking |
| `pending_payment` → `paid` | Verified provider notification, or cashier confirmation | Amount matches total + convenience fee |
| `pending_payment` → `cancelled` | Hold expires (`hold_expired`); arrival cutoff passes unpaid (`no_show`); client cancels (`client_cancelled`) | Slot capacity is released in the same transaction. The expiry job waits while a Payment is `initiated` or `pending` and younger than the payment timeout. System cancellations are audited with no actor. |
| `paid` → `completed` | Every Booking Item is `issued`, `rejected`, or `no_show` |  |
| `completed` → `paid` | An approver overrides a rejected Booking Item to `cleared` (PRC-3) | Only through `BookingService.overrideItem`, audited as `booking.reopened` with the reason. The Booking completes again once every item is final. Items of a cancelled, refund-requested, refunded or forfeited Booking cannot be overridden. |
| `paid` → `forfeited` | Forfeiture Policy applies after a no-show | Refund Request of kind `forfeiture` approved |
| `paid` → `refund_requested` → `refunded` | Refund Request approved, then marked settled | `payments.refunds:approve` |

The three client-facing statuses required by Annex B map as: Pending = `pending_approval` or `pending_payment`; Paid = `paid`, `completed` or `refund_requested` (BOQ still holds the money; the client sees a "Refund in progress" label, per Sir Sean); Cancelled = `cancelled`, `rejected`, `forfeited`, or `refunded`.

Every transition writes the Booking row, then an Audit Entry in the same transaction, then queues Notifications.

### 5.2 Booking Item

```
booked ──► checked_in ──► in_assessment ──► cleared ──► issued
   │                           │   ▲
   ▼                           ▼   │
no_show                     returned         rejected (from in_assessment)
```

`checked_in` is refused unless the parent Booking is `paid`. `cleared` goes to `pending_head_approval` first when the Service has `requires_approval`. PRC-3: a holder of `processing.assessments:approve` inside Scope, who did not perform the clearing Assessment, moves `pending_head_approval` to `cleared` (approve) or back to `in_assessment` (send back, notes required). A `rejected` item stays final for the state machine, but an approver may override it to `cleared` with a mandatory reason; the override is audited with the before and after state. A `returned` item goes back to `in_assessment` when staff open it again after the client corrects it. When the Service issues a Document with `auto_issue` on, every move to `cleared` (an officer's clear with no head approval, a head approval, or an override) continues to `issued` in the same transaction (CRT-1a); only the vaccination record issues this way, and a Sanitary Permit or Ship Sanitation Certificate is issued afterwards by the officer (CRT-5). CRT-6: a seminar roster marks a paid attendee present by taking the item `booked` to `checked_in`, `in_assessment` and `cleared` in one transaction, through `BookingService` and with the same PRC-4 required-step check as the processing screens, and marks an absentee `no_show` (possible only from `booked`); an unpaid Booking cannot be marked either way. The Booking moves to `completed` once every item is `issued`, `rejected`, or `no_show`.
- **Rescheduling (`BKG-5`):** A client with `bookings.own:reschedule` may move a `booked` item on a `pending_payment` or `paid` booking to another active, non-full `schedule_slot` for the same `service_id` and `location_id` when `reschedule_count < booking.max_reschedules` and the current slot starts at least `booking.reschedule_min_hours_before` hours in the future. Both `schedule_slots` rows are locked in ascending `id` order (`Flow B`), their `booked_count` values are adjusted, `reschedule_count` increments by `1`, and existing `payments` are unchanged.

### 5.3 Payment

```
initiated ──► pending ──► succeeded ──► refunded
                 ├──► failed
                 └──► expired
```

`succeeded` is terminal for money in. A late `succeeded` on a `cancelled` Booking sets `needs_review` on the Payment and leaves the Booking cancelled (Flow C).

## 7. Additions for TOR items built on assumptions (2026-11-13)

These support tickets ADM-9, ADM-10, PRC-4, CRT-9, CRT-10, PAY-10, RPT-6, and RPT-7. The assumptions are listed in the PRD.

New permission keys:

* `settings.changes:approve` — approve major configuration changes. Seeded to Super Admin only; System Admin holds every other settings key.
* `payments.deposits:verify` — verify a collecting officer's deposits. Seeded to Module Admin.

Role changes: Module Admin also holds `settings.services:manage`, limited by Scope. A seeded Collecting Officer (RCO) role holds the same grants as Cashier.

New terms and tables:

* **Policy Document** (`policy_documents`, `policy_acceptances`): a written policy shown at booking; a client's acceptance is stored with its version. Owner: admin-settings.
* **Change Request** (`change_requests`): a major configuration change held until a holder of `settings.changes:approve` approves it. Only `ChangeApprovalService` applies it. Owner: admin-settings.
* **Service Step** (`service_steps`, `step_results`): an ordered station a Booking Item passes through, such as Laboratory, X-ray, Evaluation, with a recorded, versioned result. Only the processing module writes results. Owner: processing.
* **Collection Report** (`collection_reports`, `deposits`): a collecting officer's closed day of onsite Payments and the deposits recorded against it; `open → closed → verified`. Owner: payments.
* **Dashboard Layout** (`dashboard_layouts`): the components a user, or a role by default, sees on the dashboard. Owner: reports.
* **Report Definition** (`report_definitions`): a saved custom report: category, columns, filters, grouping, and the role it is shared with. Owner: reports.

New document types: `pe-medical-certificate`, `food-export-certificate`, `water-analysis-certificate`.

CRT-10 uses the `food-export-water` Service Category. The `FOOD-EXPORT`
Service issues `food-export-certificate`, using the questionnaire submission
stored for the Booking Item and its original Form Template version. The
`WATER-TESTING` Service issues `water-analysis-certificate`, using the latest
recorded result of its required Laboratory analysis Step. Certificate numbers
use the prefixes `FEX` and `WAC`.

Water parameter outcomes are entered by the analyst. At least one parameter
is required. The overall outcome is `fail` if any parameter failed and
`pass` otherwise. The Document can be issued in either case. The outcome is
stored as `analysisOutcome` in `documents.payload` and is distinct from
`documents.status`, which tracks whether the Document is valid, revoked, or
superseded. Public verification may show `analysisOutcome` for Water Analysis
Certificates while keeping the parameter results and questionnaires private.

Both Services are seeded inactive with zero fees. BOQ configures the fee,
activates the Service, and opens appointment slots before it is offered.
